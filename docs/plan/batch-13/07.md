# Batch 13, item 7: a desync after an NPC's help against raiders (SOS-223)

Status: code ready, waiting for the lead's test. Engine fix in SOSDET `b13-07`; test tooling in both repositories.

## What happened

- Fray2 got vanilla's "Help!" message (`MessAlly.Help`): a raider wanted to pass through a neighbouring NPC kingdom. Fray2 pressed **Request Assistance**. That is the engine's command 9002 (`raiderAllyHelp`), at step 128918 in the host's log `20261117-232014`.
- Half a game day later, `RaidingCurrent` runs `MessAlly.fight`. The raider won: `FACTIONS.remove` gave the kingdom's land to the rebels, and `MessDestroy` ("Raider destroys!") went to Fray2.
- At step 138150 the hashes split, `clock` only: the host counted 248017 world draws, Fray2's PC 248018. One draw more, on Fray2's PC only. A resync cleared it.
- The timing fits exactly. A game day is 1152 s, a step at 5x is 1/16 s, so half a day is 9216 steps: 128918 + 9216 = 138134. The next hash after that is 138150.

## Cause (proven from the logs and the source)

- Since SOS-89 a message is sent only on the PC whose player it is for (`Message.send`, patch 16, `Hooks.messageHere`). The other PCs skip it.
- `Messages.add` builds the message's window at once (`makeSection` → `make`), inside the step.
- `MessDestroy.make` picks its text at random: `raiderMess.allyDead.rnd()`, which draws from `RND`. Inside the step that is the simulation's stream, and in the world part it counts as a world draw.
- So the PC of the raided player drew once more than every other PC. The stream is reseeded every step and nothing hashed drew after it in that step, so only the `clock` section differed. A later draw in the same step would have split the state too.
- The other probable sources the plan named are clean:
  - `MessAlly.fight`'s `RND.rFloat()` runs in `RAIDING.update` on every PC, with the raided human current (`currentHumanSwap`).
  - `allyHelp.rnd()` and `allyFight.rnd()` are picked before `send`, so on every PC.
  - `FACTIONS.remove(npc, true)`: the world log, the armies' disband and `RD.clearFaction` run on every PC, and hold nothing per PC.
- The same holds for every message whose window draws while it is built, not only this one (for example `RaiderText`'s `{player}` insert draws `RND.rInt()`). A viewed city may be the same case: the owner's PC builds its city's messages, the viewer's PC doesn't, so such a draw would split the viewed city's own stream inside that step (not proven; passed to item 11 + 12).

## The fix (engine)

- `Message.send` (patch `16-humans-world`, which already owns `Message.java`) builds the window between `Hooks.cosmeticBegin()` and `cosmeticEnd()`. Every random pick a message's window makes is now cosmetic, on every PC, for every message.
- `docs/hooks.md` and `docs/architecture.md` list it.
- It changes the draw count of any session that sends a message with such a window. The rig's recordings are all `RECORD` already (CLAUDE.md), so nothing new to record.
