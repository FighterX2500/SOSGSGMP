## What the logs show

The log kept only the summary, so which field differs is unknown.

## Cause (probable, not proven)

- The view: some division state of Fray2's city is not restored the same on the owner's PC and the viewer's after the same save loads. Views of Adam's city and watches of Fray2's battles were fine, so it is something in that city's divisions.
- The loop: per-PC state that a whole-game load resets and a world load keeps decides how many world draws a PC makes in the seconds after a world load. A view puts the viewer and the owner through whole loads and every other PC through world loads only, so after a view the PCs hold that state differently. Each world resync then splits the draw count again, so resyncs can't clear it; a whole reload of the campaign does.
- Only the count differs, so the extra draws change nothing the world hash covers, at least for minutes. They are still a desync by the rules: the clock is hashed to catch a split before it reaches the world.
- Looked at and ruled out: the resync does set the world draw count (`worldResyncLoad` → `Streams.worldDraws`); view loads keep the counts (`viewLoaded`, `ownCityBack`); the world's unsaved state (move remainders, pools, timers, court days, peace times) travels with every load. `WorldStatics.reset()` runs on whole loads only, never on a world load, which breaks the determinism rule for resyncs, but the statics it resets are tick stamps and the city's garrison sums, which don't explain a repeated 36-draw difference.
- Item 7's cause fits the loop's shape (lead's note, 2026-11-18). Since SOS-89 a message window is built only on the PC whose player it is for, and a window that picks a random text draws from the world stream there only: a `clock`-only split, with nothing in the world hash. The loop's small differences between Fray2 and Adam (1 to 3 draws) look like that. A window built after each world load, for one player only, would also explain why resyncs never clear it, and why a different PC drifts in each incident. Item 7's fix (b13-07, patch `16-humans-world`: `Message.send` builds the window as cosmetic) may end the loop; nothing here changes that line.
- It doesn't fit the view's split. There the city's draws matched (the view's `clock` section was equal) and only `divisions` differed, so no extra draw on one PC caused it.

## Why there's no fix yet

The draws that differ come from game code that only a running game shows. Neither the view's division difference nor the loop can be reproduced in a unit or loopback test: both need the game's own state after a whole load. So this round adds what the next run needs to name the code:

- **Engine** (`Engine.java`, `docs/api.md`): `viewDesyncReport()`, the viewer's whole report of a view's lost step, with the divisions it hashed; `hashedDivisions(step)` and `hashInterval()`, the divisions this PC hashed at a step.
- **Mod** (`MpViews`, `EnginePlay`): the `viewdesync` line now carries that whole report. The owner and the viewer each log `viewdivs`, the city's divisions at the view's first two hash steps, so both logs show which field differs whatever happens.
- **Test tooling** (`MpAutopilotCommands`): the autopilot command `trace desync` traces every world draw, and at each desync this PC finds writes `trace-<step>.txt` next to the autopilot's events file: the draws of the 150 steps before it, one call site a line. The same file from two PCs differs first at the code that drew on one of them only.

No message, save or protocol changes. Nothing in the step changes.

## Result of the first run (2026-11-18, 14:09 to 14:32)

The lead ran `view11.py` on b13-A (item 7's change merged first, then this branch), save 98, three games on one PC. Logs: `C:/ClaudeFolder/SOS-wt/b13-results/A/view11/`.

- Neither bug showed. All three views held 2 minutes (steps 4320 to 13950, 37980 to 47580, 70980 to 80580). There was no `viewdesync`, no world desync in 527 hashes, and no trace file. twopc passed, and no game wrote an error file.
- The views really ran Fray2's city: the host loaded the joiner's save (2.31 MB, as Fray2's real city was) at each freeze in 8 to 10 s.
- The `viewdivs` lines of the host and Fray2's game match field for field at all six hash steps. Fray2's city in this save has two divisions with men (0 and 4), and Fray2's 23:18 city had four.
- The world hashes, so the world draw counts, matched every 30 steps, through every freeze and thaw.

What this proves, and what it doesn't:

- It doesn't prove item 7's change fixed either bug. This run starts from a fresh resume: every PC had just loaded the whole game, and the views came 1, 9 and 17 minutes in. Both playtest failures came after 40 minutes or more of play since the last whole load, and the 01:59 one after a view of Adam's city. The per-PC state this file suspects builds up over such a stretch. So this run may simply not reach it, with or without item 7.
- Item 12 fits item 7's mechanism (a window built on one PC drawing a world random): only the world draw count differed, the world never did, and Fray2 and Adam differed by 1 to 3 draws. The fixed 35 and 110 draws after each resync would then be a window that a world load brings back on one PC. That is plausible, not shown.
- Item 11 doesn't fit it. In both lost steps the view's clock, which counts the city's draws, matched; only `divisions` differed. So no extra draw on one PC split the city. A class that would fit is a write to a division by this PC's rendering or UI, which draws nothing. One example is `DivSettings.ammo()`, which writes `ammoI` and `aref` and is called by the soldiers' sprites (`HSprites`). `fireAtWill()` is another: it clears the flag when it finds no ammo. Both fields are in the divisions hash. The owner and the viewer look at different parts of the city. This is a candidate only; the next lost step's `viewdivs` lines would name the field.

What would settle it: the same `view11.py` run on this branch alone (engine and mod `b13-11`: today's main plus this logging, without item 7).

- If it reproduces either bug and b13-A doesn't, batch A's only simulation change, item 7's, fixes what reproduced. That run's `viewdivs`, `viewdesync` report and trace files then show the mechanism.
- If it doesn't reproduce either, `view11.py` doesn't reach the playtest's conditions, and the next playtest with this logging is the test.
- The pack-1117 build can't serve: its autopilot has no `trace desync`, and it logs neither `viewdivs` nor the whole report.

## The contrast run (2026-11-18, 19:07 to 19:34)

The owner approved it. The lead ran the same `view11.py` on this branch alone (engine 6af685e, without item 7). Logs: `C:/ClaudeFolder/SOS-wt/b13-results/A/view11-contrast-b13-11/`. All three views held 2 minutes, there was no world desync, and twopc passed: the same as on batch A.

**Both runs did have three players at 5x.** Two lines in the runner's output looked as if they hadn't:

- twopc printed "host: removed at the start: [2]". That is the wording of twopc's resume verdict for any `retired` event. Here slot 2 retired at step 104310 (104820 in the contrast run), in the last minute of the run. Game 3 reached its `endat` step and left first, and the host removed it then. Until then every `identity` event lists slots 0, 1 and 2, and every host status line has a peer called Local.
- The status events said speed 1.0 only at the end. The agreed speed was 5 for 133 of 141 status events (134 of 141 in the contrast run). The exceptions were two short catch-ups after the views' loads, and 1x in the last minute, when the joiner's battle against NPCs began.

So `view11.py` needed no fix for that.

**What we can say now.** The bugs didn't show with item 7's change, and didn't show without it either. So this `view11.py`, a fresh resume with the first view a minute in, doesn't reach what the playtest reached. The batch A pass says nothing about whether item 7's change fixes 11 or 12. Both stay as before: not reproduced, causes probable only. Item 12 fits item 7's mechanism; item 11 doesn't.

**A longer run.** `view11.py` now takes:

- `--first-run S`: seconds of play before the first view. 2400 matches the 40 minutes the playtest ran since its last whole load.
- `--adam-view S`: first the host views Adam Smasher's city that long, as at 01:55. 210 matches the 3.5 minutes it lasted.

Even so, the autopilot's players make no deals, trades or wars and never move a camera, and all three games share one PC. If item 11 is a write to a division from what a player's screen shows, as suspected, they won't reach it. A long run that passes proves as little as the short ones did.

Recommendation: no more contrast runs. If the owner wants one more run, make it the long one, once, on the build that ships (b13-A), as a 75-minute soak of the batch. If it shows a lost step or the loop, its `viewdivs` lines and trace files name the cause, and a contrast run then becomes worth its time. Otherwise the batch ships with this logging, and the next real playtest is the test of 11 and 12.
