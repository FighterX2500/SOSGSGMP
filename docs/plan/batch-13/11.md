Agent for item 11 (Jira SOS-222). Branches: mod `b13-11`, engine `b13-11`. Status: the cause is narrowed down, not proven. This round adds the logging and the trace that name it; the fix follows from the next run's files.

## What the logs show

Sources: host logs `20261117-223957` and `20261118-012021`; Fray2's `20261117-193957-join` and `20261117-222020-join`; Adam Smasher's `20261117-224006-join` and `20261118-012029-join` (all in `sosgsgmp`). Fray2's clock runs 3 hours behind the host's: Fray2's 20:18 is the host's 23:18.

The log kept only the summary, so which field differs is unknown.

## Cause (probable, not proven)

- The view: some division state of Fray2's city is not restored the same on the owner's PC and the viewer's after the same save loads. Views of Adam's city and watches of Fray2's battles were fine, so it is something in that city's divisions.
- The loop: per-PC state that a whole-game load resets and a world load keeps decides how many world draws a PC makes in the seconds after a world load. A view puts the viewer and the owner through whole loads and every other PC through world loads only, so after a view the PCs hold that state differently. Each world resync then splits the draw count again, so resyncs can't clear it; a whole reload of the campaign does.
- Only the count differs, so the extra draws change nothing the world hash covers, at least for minutes. They are still a desync by the rules: the clock is hashed to catch a split before it reaches the world.
- Looked at and ruled out: the resync does set the world draw count (`worldResyncLoad` → `Streams.worldDraws`); view loads keep the counts (`viewLoaded`, `ownCityBack`); the world's unsaved state (move remainders, pools, timers, court days, peace times) travels with every load. `WorldStatics.reset()` runs on whole loads only, never on a world load, which breaks the determinism rule for resyncs, but the statics it resets are tick stamps and the city's garrison sums, which don't explain a repeated 36-draw difference.
- Item 7's cause fits the loop's shape (lead's note, 2026-11-18). Since SOS-89 a message window is built only on the PC whose player it is for, and a window that picks a random text draws from the world stream there only: a `clock`-only split, with nothing in the world hash. The loop's small differences between Fray2 and Adam (1 to 3 draws) look like that. A window built after each world load, for one player only, would also explain why resyncs never clear it, and why a different PC drifts in each incident. Item 7's fix (b13-07, patch `16-humans-world`: `Message.send` builds the window as cosmetic) may end the loop; nothing here changes that line.
- It doesn't fit the view's split. There the city's draws matched (the view's `clock` section was equal) and only `divisions` differed, so no extra draw on one PC caused it.

## Why there's no fix yet

The draws that differ come from game code that only a running game shows. Neither the view's division difference nor the loop can be reproduced in a unit or loopback test: both need the game's own state after a whole load. So this round adds what the next run needs to name the code:

- **Engine** (`Engine.java`, `docs/api.md`): `viewDesyncReport()`, the viewer's whole report of a view's lost step, with the divisions it hashed; `hashedDivisions(step)` and `hashInterval()`, the divisions this PC hashed at a step.
- **Mod** (`MpViews`, `EnginePlay`): the `viewdesync` line now carries that whole report. The owner and the viewer each log `viewdivs`, the city's divisions at the view's first two hash steps, so both logs show which field differs whatever happens.
- **Test tooling** (`MpAutopilotCommands`): the autopilot command `trace desync` traces every world draw, and at each desync this PC finds writes `trace-<step>.txt` next to the autopilot's events file: the draws of the 150 steps before it, one call site a line. The same file from two PCs differs first at the code that drew on one of them only.

No message, save or protocol changes. Nothing in the step changes.
