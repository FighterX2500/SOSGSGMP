# Batch 13, item 4: the resume lobby's saves list scrolls (SOS-228)

Spec section 11 (Resuming). No rule changes.

## What happened

In the 2026-11-17 playtest, Load Saved Lobby showed about 10 saves and no more. Older saves couldn't be reached.

## Cause (proven, from the source)

`MpScreenResume` built a fixed column of 12 rows (`ROWS = 12`). `open()` copied the store's records into it and stopped at the 12th (`if (records.size() == ROWS) break;`). There was no scrolling, so the 13th save and every older one were never listed.

The order was already right. `CampaignStore.all()` sorts by the record's time, newest first, and a tie by the higher number first. `theStoreListsNewestFirstFindsAndNumbers` already tested it with three records.

## The fix

- `MpScreenResume` now lists every save in vanilla's scrolling list, as vanilla's load screen (`view.menu.MenuScreenLoad`) does. `GScrollable` holds 12 rows of type `Scrollable.ScrollRow`. Each row is told which save to show as the list scrolls. The list scrolls with the mouse wheel and has the game's slider on its right.
- Each save's line is a `GText` made in `open()`, not in render, so drawing a row allocates nothing.
- `open()` scrolls back to the top, so the newest save is at the top each time the screen opens.
- A row's selection, active state and click work as before, by the save's index in the list instead of by the row.
- `MpSaves` didn't need a change: `MpSaves.store()` gives the store, and the store's order is the one the list shows.

## Test tooling added

- **Autopilot `resume=oldest`** (host, over IP; `MpAutopilot`). The host doesn't build the resume settings itself. It sets its name and port as Create Lobby would, then opens Load Saved Lobby. The screen's `hover` (every frame) hands control to `MpAutopilot.resumeScreen`, which:
  1. sends the event `resumelist` with the number of saves listed;
  2. after 2 s, takes a screenshot (`guishot` `resumetop`: the newest saves);
  3. after 3 s, scrolls the list to its end, as the slider does (`Scrollable.set(max)`), and clicks the last row: the oldest save;
  4. after 5 s, takes a screenshot (`guishot` `resumeoldest`: the oldest saves, the last one picked);
  5. after 6 s, presses Host (IP), and sends `resume` with the campaign, the number, the file and `saves`, then `lobby`.
- **twopc `--copies N`** (with `--campaign ID:NUMBER --here`). The host's data folder gets N more records of the seeded save, numbered NUMBER+1 to NUMBER+N, each a minute newer. All of them name the same game save, so they all show as present. The seeded save is then the oldest of N+1. The host runs with `resume=oldest`. The joiner has only save NUMBER, so the resume works only if the host picked the oldest. The verdict also checks that the host's `resume` event has number NUMBER and `saves` N+1, and that both screenshots were taken.
